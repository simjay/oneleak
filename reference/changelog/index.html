    Changelog¶

    All notable changes to this project are documented in this file. Format follows Keep a Changelog, and versioning follows Semantic Versioning.

    Unreleased¶

    Added¶

    • scanner.py split into four modules. It had grown to 713 lines doing six unrelated jobs, the same shape as the old test_scanner.py. Now: scanner.py (415) finds things, skip_rules.py (123) decides which rules get switched off in which kinds of file, reading.py (90) turns bytes on disk into text, findings.py (83) turns a match into something safe to show, and config.py gained the two helpers that adjust path patterns when a scan starts in a subfolder. No compatibility shims: the six import sites were updated directly, so there is one way to import each thing. oneleaks.scan and oneleaks.scanner.scan are unchanged, which keeps the public API and the mkdocstrings reference in the API docs working. Folder walking stayed with scan_text rather than moving to reading.py, because splitting them would have created a circular import.
    • Docs grouped into folders, matching the sections mkdocs.yml already declared: getting-started/, guides/, advanced/, reference/. mkdocs-redirects is now a docs dependency and maps every previous URL to its new home, so an existing link to /en/latest/mcp/ still lands on the MCP page. 40 cross-links between docs were rewritten; mkdocs build --strict fails on any that are wrong, which is what caught them.
    • Tests moved next to what they test. test_scanner.py held 167 of the 397 tests, most of which checked whether a particular vendor's key format was detected. That is a test of the rule list, not of the scanner. Those 110 tests now live in integration/secrets/test_secret_rules.py, and the personal-data ones in integration/pii/test_pii_rules.py, so each of those files covers everything about its own rules: that the list loads, and that the rules find what they should. integration/scanning/test_scanner.py keeps the scanning machinery, and dropped from 167 tests to 45. Nothing was added or removed in the move: 397 test functions and 424 collected tests before and after.
    • tests/ is now grouped into folders. It was 18 files in one flat directory with a single subfolder, which gave no clue where anything belonged. The top level now says how a test runs (unit/, integration/, e2e/), and folders inside say what it covers (secrets/, pii/, scanning/, output/, commands/, false_positives/). tests/README.md lists what goes where. Move only: 397 test functions and 424 collected tests before and after.
    • Tests that check oneleaks does not report things that are not secrets. tests/integration/false_positives/clean_files/ holds eight safe files that oneleaks used to report by mistake, each copied from a real project and cut down to the smallest version that still showed the problem. Each one has a note at the top saying, in plain words, what mistake it guards against. The test beside it scans every file and checks nothing is reported, so if a rule change starts flagging safe content again, the test fails and the file explains why it was safe. Tests for secrets we do want found stay in Python and build their fake keys in code, because a file full of realistic-looking keys makes GitHub refuse the push. CONTRIBUTING.md explains where to add each kind.
    • Pre-commit hook, GitHub Action and SARIF output. .pre-commit-hooks.yaml exposes three hooks (oneleaks for staged content, oneleaks-files for the files a commit touches, oneleaks-push for the working tree on pre-push), so other repositories can consume oneleaks without writing their own wrapper. action.yml is a composite Action taking args, version, fail-on and sarif-file. oneleaks scan --sarif PATH writes a SARIF 2.1.0 log: every rule that produced a result is declared in tool.driver.rules (GitHub drops results whose ruleId has no descriptor), the four severities map onto SARIF's three levels, and Finding.fingerprint becomes a partialFingerprints entry so GitHub tracks a finding across runs instead of reopening it. Previews rather than raw values reach the report, as everywhere else.
    • --category and --severity on oneleaks scan, plus a summary line. The README has always claimed you can route secrets and PII separately, but that was only reachable from the Python API. Both flags narrow the reported set, so human output, --json, --sarif and the exit code all agree; --fail-on is unchanged and still moves only the exit code. Human output now ends with 3 findings: 1 critical, 1 high, 1 low.
    • 8 new provider rules for credential formats the existing rules could not express: slack-app-token (xapp-), slack-config-access-token and slack-config-refresh-token (the xoxe rotation pair), gitlab-runner-registration-token (GR1348941), heroku-api-key-v2 (HRKU-), huggingface-org-token (api_org_), aws-bedrock-api-key (ABSK), and cloudflare-origin-ca-key (v1.0-). Also stripe-test-key, split out at medium rather than folded into the live-key rules, because a test-mode key reaches no real money and the severity criteria in secrets.yaml put it below them.
    • Logo: a drop struck through by a rule that runs past the silhouette and erases it only where it crosses, echoing the one[leaks] logotype's redaction bar. Shipped as four single-path SVGs under docs/assets/, each with the fill its context needs: mark-on-dark.svg (docs header, README on dark), mark-on-light.svg (README on light), favicon.svg (carries its own prefers-color-scheme switch, since a favicon is loaded as a standalone document), and mark.svg (currentColor, for inline embedding). Wired to theme.logo/theme.favicon in mkdocs.yml and to a <picture> banner in the README. Note that material renders theme.logo into an <img>, where currentColor would resolve to black and vanish against the indigo header, which is why the fills are explicit rather than inherited.
    • End-to-end test suite: tests/e2e/test_cli_subprocess.py spawns oneleaks as a real subprocess (sys.executable -m oneleaks.cli, no PATH dependency) covering scan/sanitize/desanitize/baseline/git-scanning/config-discovery through the real process boundary — real exit codes, real stdin/stdout/stderr, real git subprocesses, real file permissions. tests/e2e/test_mcp_stdio.py spawns the MCP server and talks to it over real stdio using the mcp SDK's client transport (ClientSession/stdio_client), confirming the server actually starts, registers its four tools, and responds correctly to a real client, which tests/integration/commands/test_mcp_server.py's direct-function tests don't cover (deliberately: protocol framing is the SDK's responsibility, not oneleaks's, but "does it actually run" is). Found and fixed one real bug in the process: DEFAULT_EXCLUDED_DIR_NAMES didn't include .pytest_cache/.mypy_cache/.ruff_cache/.hypothesis, so a local oneleaks scan . after running the test suite picked up false positives from cached test node IDs.
    • 20 new built-in provider/structural secret rules: AI/dev-tool (huggingface-token, replicate-api-token, groq-api-key), cloud/infra (aws-temp-access-key-id, digitalocean-pat, cloudflare-api-token, vault-service-token, docker-hub-pat), SaaS (sendgrid-api-key, postman-api-key, sentry-auth-token, newrelic-api-key, planetscale-token, supabase-access-token, shopify-access-token), messaging (discord-bot-token, discord-webhook-url, telegram-bot-token), and structural anchors (pgp-private-key, http-basic-auth-credential). 3 new PII rules: imei (validated via the existing luhn validator, which is also IMEI's real check-digit algorithm), mac-address, and bank-routing-number (keyword-gated, new aba_routing validator). All three new PII types are toggleable via .oneleaks.yaml's pii: block like the existing seven.
    • 13 more built-in provider secret rules (second batch): terraform-cloud-token, google-oauth-client-secret, heroku-api-key (keyword-gated), mailchimp-api-key, square-access-token, square-oauth-secret, stripe-webhook-secret, linear-api-key, notion-integration-token, airtable-pat, mapbox-secret-token, algolia-admin-api-key (keyword-gated), facebook-access-token. mapbox-secret-token and facebook-access-token are lower-confidence than the rest of the rule set (approximate format / short 3-char prefix respectively) and are candidates for revisiting if they prove noisy in practice.
    • Project tooling: Makefile, GitHub Actions CI, tag-triggered PyPI trusted-publish workflow, pre-commit dogfooding config, MkDocs + Material docs site.
    • severity_overrides in .oneleaks.yaml is now applied to findings (previously parsed but unused). Values are validated against the known severity levels.
    • Git history scanning: oneleaks.git.scan_history() / oneleaks scan --history scans commit history for secrets, including ones later removed from the working tree, something scan()/scan_changed()/scan_staged() cannot see, since they only look at current content. Defaults to the current branch's history capped at the most recent 5000 commits (--since/--max-commits/--all-refs to override). Truncation is always reported, never silent. Detection runs per-commit, per-diff-hunk (only what each commit actually added, with each hunk's added lines joined into one block so multi-line formats like PEM keys still match correctly), not a full-file rescan at every commit. Finding.commit and ScanResult.truncated are new fields supporting this.
    • MCP server (oneleaks[mcp], oneleaks-mcp command): exposes scan_text, scan_path, sanitize_text, desanitize_text as MCP tools over stdio, for agent runtimes to call directly instead of shelling out to the CLI. Config auto-discovery matches CLI behavior. See docs/guides/mcp.md.
    • Provider rule test coverage for GitLab, Slack, Twilio, Datadog, Google, and PyPI (positive/negative/boundary cases).
    • Hypothesis property tests (tests/test_properties.py): Luhn, IBAN, sanitization offsets, overlap resolution, and config-schema validation.
    • scripts/benchmark.py / make bench: prints timing for 1KB/1MB text, a config-sized input, small/large synthetic repos, and git.scan_changed(). An observability script, not a CI gate.
    • AGENTS.md: repo orientation for coding agents (setup, commands, load-bearing ordering decisions, conventions).
    • docs/advanced/architecture.md: detailed explanation of the detection pipeline and sanitization algorithm, stage by stage. The "advanced" doc previously only in internal (untracked) notes.
    • .github/workflows/docs.yml + make docs-deploy: publishes docs to GitHub Pages on push to main. Read the Docs (the primary host) still builds via its own webhook once connected, and no GitHub Action can drive that directly, but this workflow optionally triggers an RTD API build too, if RTD_API_TOKEN/RTD_PROJECT_SLUG are configured.
    • Explicit [tool.ruff.lint] select in pyproject.toml (including I, isort-equivalent import sorting) instead of relying on the installed ruff version's implicit default rule set.

    Fixed¶

    • Git scans silently skipped UTF-16 files that a folder scan reads fine. git.py carried its own decoder that only understood UTF-8, so the byte-order-mark handling added for oneleaks scan . never applied to --staged, --changed or --history. On a repo holding one UTF-8 and one UTF-16 file with the same secret, a folder scan reported two findings and a staged scan reported one. The duplicate decoder is gone and git scanning now uses the same reading.py code path as everything else.
    • version: in .oneleaks.yaml was documented, parsed, and then ignored. A config claiming version: 99 was accepted silently and run under version-1 rules, applying settings its author never asked for. It is now checked, with the same message shape baseline files already used for their own version field.
    • URL paths were reported as high-entropy secrets. / is in the base64 alphabet, so github.com/psf/requests/security/advisories/GHSA-... reads as one long candidate. These score 4.32 to 4.66 against a 4.3 threshold, inside the range real tokens occupy (median 4.85, low end 4.18), so no threshold separates them and the shape has to: a candidate with two or more lowercase-word segments between slashes is a path. Restricted to lowercase deliberately. Allowing mixed case catches five more false positives out of 41 but wrongly suppresses about 1% of real base64 tokens, measured over 8000; lowercase-only costs 1 in 8000. Two other approaches were measured and rejected: dropping / from the candidate alphabet made one repository worse and lost 20% of slash-bearing tokens, and no entropy threshold separates the two populations at all.
    • Program text was reported as a credential. The generic-assignment detector read a function signature, a call expression and an English phrase as <keyword> <separator> <value>. Values containing whitespace or any of ()<>| are now treated as expressions rather than literals, and an unquoted purely alphabetic value is treated as an identifier or type annotation. Quoted values are exempt, so an all-letter passphrase in quotes still reports.
    • Documented proxy credentials were reported. http://user:pass@host is how every proxy tutorial is written, and both the basic-auth rule and the email rule fired on it: the latter read pass@proxy.example.org as an address. The known filler words are now shared with the rule-level placeholder check, and the email pattern skips a URL's userinfo while still matching mailto:.
    • 127.0.0.1 was reported as personally identifiable information. So were 0.0.0.0, every RFC 1918 private address, link-local, multicast and the RFC 5737 / RFC 3849 documentation ranges. These appear in the configs, tests and docs of essentially every repository: on three real projects (psf/requests, pallets/flask, expressjs/express) they were the single largest source of findings, and every one was noise. The built-in ipv4/ipv6 rules now use new public_ipv4/public_ipv6 validators that additionally require the address to be routable. The plain ipv4/ipv6 validators are unchanged and still available to custom rules that want every address. Measured effect on total findings: flask 118 to 43, express 96 to 67, requests 519 to 415.
    • Certificates and drawings caused a flood of wrong reports. A certificate is meant to be shared, so it holds no secret, but it is stored as a block of random-looking text just like a private key is. One project's test certificates alone caused 118 wrong reports. Drawings are a similar story: an SVG is stored as long lists of numbers, and four numbers in a row look exactly like an IP address, which produced 81 wrong reports across 15 real SVG files. Inside a certificate block we now turn off the two rules that flag a value for looking random, and inside .svg files we turn off the IP address rule. Blocks labelled PRIVATE KEY are untouched, so real private keys are still reported. In each case we only turn off rules we actually watched go wrong on that kind of file. Together with the IP address fix below, psf/requests went from 519 reports to 126.
    • Five provider patterns missed credential formats the vendor issues. stripe-secret-key accepted only sk_live_, stripe-restricted-key only rk_live_ (missing rk_prod_, a live production key), openai-api-key accepted proj and svcacct but not admin, and heroku-api-key was lowercase-hex only so an uppercase UUID slipped through. slack-webhook-url required https:// and the /services/ path, missing http://, scheme-less URLs, and the newer /workflows/ and /triggers/ forms.
    • AWS's own example key was reported as a real one. AKIAIOSFODNN7EXAMPLE is copied into thousands of tutorials and config files. Rules that look for secrets now ignore a value containing a word that says it is only an example (example, placeholder, randomstring and similar). Kept deliberately narrow. Rules of thumb like "the same character repeated many times" or the word xxxxx seem safe but a real key is allowed to contain either, and missing a real key is far worse than reporting an example. Personal data is not affected, since an email address in documentation is still an address someone asked us to hide.
    • A first scan of any Go or Node project produced hundreds of wrong reports. Lock files record a project's dependencies. They are written by tools, not people, and are almost entirely long random-looking checksums, which is exactly what a key looks like. Two real lock files, from npm and from Go, produced 816 wrong reports between them. 22 lock files are now recognised by name (go.sum, package-lock.json, yarn.lock, pnpm-lock.yaml, Cargo.lock, poetry.lock, uv.lock, Gemfile.lock, composer.lock, flake.lock and others), and the two rules that flag a value for looking random are switched off in them. Only those two, never the whole file, because a lock file really can contain a login: a download URL can carry a username and password, and the rules that catch those keep running. This also removed the uv.lock workaround from this repo's own .oneleaks.yaml. The trade-off: a genuinely random secret pasted into a lock file is now missed unless one of the other rules recognises it.
    • credit-card reported Go module pseudo-versions as high-severity findings. The rule's pattern allows its [ -] separator anywhere, so golang.org/x/crypto v0.0.0-20190510104115-cbcb75029529 reads as a 17-digit run, and Luhn accepts roughly one digit sequence in ten by chance. 14 such findings came out of a single go.sum, and they appear in go.mod and any other file carrying pseudo-versions or timestamps. Tightening the separator grouping does not help, because the bare 14-digit timestamp is itself Luhn-valid and 13-19 consecutive digits is a legitimate card shape. credit-card now uses a new credit_card validator: Luhn plus an Issuer Identification Number prefix at a length that issuer actually uses. Verified against Visa/Mastercard (both series)/Amex/Discover/JCB/Diners/UnionPay/Maestro in bare, spaced and hyphenated forms, all still detected, with the 14 false positives gone. imei keeps the plain luhn validator, since IMEI has no issuer prefix. Behavior change: a Luhn-valid number with no recognizable issuer prefix is no longer reported as a card.
    • Running oneleaks from a subfolder ignored the config file completely. It only looked for .oneleaks.yaml in the folder you were standing in. So a pre-commit hook, an editor plugin, or just cd src && oneleaks scan . found no config at all and ran with every exclude, allow-path, disabled rule and severity setting missing. It now looks in each folder above too, and uses the closest one. That alone was not enough, though: people write the file patterns relative to the config file, while the paths oneleaks reports start from wherever the scan began, so the two were being compared against different starting points and quietly never matched. The config now remembers which folder it came from, and the patterns are trimmed to match before anything uses them. A config built in code has no folder and is left exactly as written. This applies when you scan a single file too, not just a folder, because oneleaks scan . and oneleaks scan leak.txt in the same place were giving different answers from the same config. Git scans need none of this, since their paths already start at the top of the repository.
    • UTF-16 files were skipped without a word. Binary detection is a null-byte check, and UTF-16 text is close to half null bytes, so a secret in a PowerShell script or a .NET config produced a scan indistinguishable from a clean one. Byte-order marks are now checked before the binary heuristic, recovering BOM-carrying UTF-16 (LE and BE, what Out-File and .NET write), UTF-32 and UTF-8-with-BOM. Known limitation: BOM-less UTF-16 has nothing to distinguish it from binary and is still skipped.
    • CI failed on every run: uv.lock was gitignored, but astral-sh/setup-uv's cache defaults to keying off it. With no uv.lock in the checkout, the cache-dependency glob matched nothing and the step errored out (Error: No file matched to [**/uv.lock]). Now tracked in git. Since uv.lock's package-hash strings are exactly the kind of high-entropy noise oneleaks flags, and git-based scans (--staged/--changed/--history) don't consult .oneleaks.yaml's exclude (only directory-walk scans do), uv.lock was also listed in allow.paths — without that, tracking it would have broken the pre-commit dogfood hook the moment anyone touched a dependency, trading one CI failure for another. (Superseded: lockfiles are now recognized by name, and both entries have been removed.)
    • .oneleaks.yaml fields weren't shape-checked before use. exclude, rule_paths, disabled_rules, allow.paths, pii, and severity_overrides all skipped validating that the YAML gave the expected shape. A list field given as a bare string (exclude: "node_modules/**" instead of ["node_modules/**"]) silently iterated it character-by-character instead of raising, making the field a silent no-op. A mapping field given as a list (pii: [email, phone] instead of {email: true, phone: true}) crashed with a raw ValueError/AttributeError instead of a clean error. Both cases now raise ConfigError naming the offending field. Both failure modes fail toward more scanning, not less: a broken exclude/allow.paths scans more than intended rather than silently missing secrets.
    • Baseline files written by write_baseline() stamp a version field that load_baseline() never checked. A baseline from an incompatible future format would have been read as if it matched the current one. load_baseline() now rejects a mismatched or missing version with a clear error.
    • A PGP private key block (pgp-private-key) got a useless generic preview (----****---) instead of the clean <PRIVATE_KEY> a PEM key gets, since _safe_preview()'s private-key branch only matched pem-private-key's type, not pgp-private-key's.
    • The same unchecked-shape problem existed in custom YAML/JSON rule loading, worse: several cases weren't even caught by ConfigError. priority: "high" (a string instead of an int) parsed cleanly and then crashed deep inside overlap resolution with a raw, unhandled TypeError. pattern: [...]/validator: [...] (a list instead of a string) crashed the same way in candidate generation. id/category/type/severity given as a non-string (e.g. id: 123) went undetected entirely. Worst of the group: keywords: "xyz" (a bare string instead of a list, a very plausible typo) didn't error at all — it silently split into individual-character keywords (tuple("xyz") == ('x','y','z')), which then matched almost any nearby text containing a common letter, quietly defeating the keyword gate a rule relies on for precision instead of raising. rules.py::_validate_entry() now shape-checks every field before build_rule() trusts it.
    • Several provider secret regexes (openai-api-key, anthropic-api-key, stripe-secret-key, stripe-restricted-key, pypi-token, plus the entropy-candidate regex) used unbounded quantifiers that could run away across trailing content with no separator. Bounded them to a realistic max length.
    • Inline # oneleaks: allow <rule-id> suppression ran after overlap resolution, so scoping suppression to one rule could accidentally suppress a different, non-allow-listed rule's finding for the same span. Suppression now runs before overlap resolution.
    • azure-storage-key's regex had an unsatisfiable trailing word-boundary and could never match anything.
    • aws-secret-access-key's bare 40-character charset match could shift across the = delimiter in KEY=value, capturing the wrong span. Now anchored on the key name + assignment operator.
    • A YAML/JSON custom rule with keywords: (or other list fields) present but null crashed with an unhandled TypeError instead of a clean ConfigError.
    • oneleaks.scan(bytes) on non-UTF8 input raised unconditionally, unlike an equivalent binary file on disk (silently skipped). The two input forms now behave consistently.
    • sanitize() (like git.scan_changed()/scan_staged() before it) called the scanner directly and bypassed .oneleaks.yaml's disabled_rules/allow.paths/severity_overrides. All three entry points now share one code path (scan_text_with_config()), closing this class of bug for good rather than patching each call site.
    • CLI: oneleaks scan <path> --changed/--staged now errors instead of silently ignoring the path argument, and --changed/--staged together is now a clean argparse error instead of --changed silently winning.
    • The generic-assignment detector's bare token keyword false-positived on non-secret values like GitHub Actions' permissions: { id-token: write }. read/write added to the placeholder-value denylist.

    Removed¶

    • Dead code swept out. _SSN_RE_STRICT in validators.py was assigned None with a comment about being populated lazily; nothing ever populated or read it. git.py::_decode duplicated reading.py::_decode_text (and was the cause of the UTF-16 bug above). The identical builtin_entries() in secret_rules.py and pii_rules.py now share one loader in rules.py; both modules stay separate, because the two categories are configured differently, but they no longer carry the same eight lines twice.
    • Dropped several unused/never-wired fields found during a bug + simplification pass: Rule.min_entropy, Rule.python_rule, Finding.confidence, RuleMatch.confidence, Config.sanitize, Rule.include_paths/exclude_paths. All were parsed/declared but never consumed anywhere in the detection pipeline. PythonRule.detect() now only accepts RuleMatch, not a bare (start, end) tuple, removing a branch used by nothing in practice.
    • Dropped the oneleaks[pii-ml] optional-dependency group until there's an actual adapter behind it. It was pure packaging plumbing with no code path.

    Added¶

    • oneleaks --version, and a real description on oneleaks --help (which previously said nothing about what the tool does).
    • Config and RuleMatch are now exported from the top-level oneleaks namespace. Previously the documented custom-rule example needed two import paths (from oneleaks import PythonRule + from oneleaks.models import RuleMatch). You could not implement the exported PythonRule without a non-exported type.
    • Baselines: oneleaks scan --baseline PATH [--update-baseline] records (rule_id, path, fingerprint) for known findings and only reports new ones, the standard adoption path for turning oneleaks on against a codebase that already has findings. New module oneleaks/baseline.py. Requires ONELEAKS_FINGERPRINT_KEY to be set (fingerprints are otherwise keyed off a random per-process value, so a baseline could never match across runs). --baseline refuses to run without it rather than silently matching nothing. Deliberately a CLI-only concept, not a Config/.oneleaks.yaml field: a baselined finding is still a real secret, and routing it through the shared config-filter pipeline would have silently stopped sanitize() from redacting it too. See docs/getting-started/configuration.md#baselines.
    • docs/advanced/concepts.md: the field knowledge behind oneleaks's design decisions (entropy, validators, fingerprinting, redaction vs. tokenization, baselines, and why some competitor techniques, like TruffleHog-style live verification and Betterleaks-style BPE token-efficiency scoring, were evaluated and not adopted).
    • docs/getting-started/configuration.md documents how to adopt oneleaks on a repo that already has findings, now via baselines rather than only partial substitutes.

    Fixed¶

    • Every "bad input file" path leaked a raw Python exception type to the user. --config missing.yaml printed error: FileNotFoundError: [Errno 2]..., a malformed .oneleaks.yaml printed a multi-line ParserError dump, a malformed --map file printed JSONDecodeError, and a mapping file missing a key printed KeyError: 'rule_id'. All now raise ConfigError with a message that names the offending file and the actual problem. Fixed at the source (config.py, rules.py, cli.py) rather than in the CLI's catch-all, so the Python API benefits too: oneleaks.scan(text, config="missing.yaml") previously raised FileNotFoundError.
    • oneleaks scan --staged outside a git repository dumped git's entire multi-thousand-character usage text (outside a repo, git diff --cached falls back to --no-index mode where --cached is not a valid option). All three git modes now fail fast and identically with error: not a git repository, and any other git failure is truncated rather than echoed in full.
    • Git errors no longer echo back the internal command oneleaks happened to run (git log --format=%H,%P failed: ... is an implementation detail, not something a user can act on).

    Changed¶

    • mkdocs pinned below 2.0 (>=1.6,<2.0), same reasoning as the existing mcp>=1.0,<2.0 pin below it. MkDocs 2.0 removes the plugin system and rewrites theming with no migration path (mkdocs-material's own announcement: https://squidfunk.github.io/mkdocs-material/blog/2026/02/18/mkdocs-2.0/), which would break this docs build outright. mkdocs-material==9.7.7 currently declares its own mkdocs<2,>=1.6 constraint, so this was harmless today, but that protection disappears the moment mkdocs-material itself ships a 2.0-compatible major version, since our own mkdocs-material>=9.5 has no upper bound. Pin the package actually undergoing the breaking change directly rather than relying on a transitive dependency's constraint that could later be loosened.
    • The Makefile sets NO_MKDOCS_2_WARNING, silencing the multi-line MkDocs 2.0 notice mkdocs-material prints on every invocation. The notice is unconditional (it never checks the installed mkdocs version), so the pin above doesn't affect it, and it's red-on-stderr in a way that reads like a build failure in CI logs while saying nothing about this project. --strict still aborts on genuine problems like broken internal links, verified.
    • Secrets and PII split into peer modules, oneleaks/secret_rules.py and oneleaks/pii_rules.py. Each owns its own builtin rule file's loading; everything else (matching engine, validators, overlap resolution, fingerprinting, sanitization) stays shared, category-agnostic code, since e.g. _resolve_overlaps() genuinely needs both categories' candidates in one pool (a connection-string password can look like an email's local@domain shape). This also fixes a real bug: the pii: config toggle used to validate against a hand-maintained set in config.py while scanner.py separately hand-maintained the type→rule_id map it disabled by, and if the two ever drifted, a type would pass validation and then silently do nothing. Both are now derived from pii_rules.py's one source of truth (pii.yaml itself), so a new builtin PII rule is automatically toggleable with no matching Python edit required, and this class of drift is no longer possible. No new config surface: secrets deliberately did not get an equivalent secrets: {} toggle, since disabled_rules: [rule-id] already covers that uniformly for every rule regardless of category. pii.yaml also gained the policy header comment secrets.yaml already had, describing the two things that are genuinely different about PII rules (evidence favors checksums over fixed prefixes; severity trends low/medium, not high/critical).
    • secrets.yaml consistency pass. The file previously had no written standard for when a rule needs a keyword gate or what severity a given access level should get, so those calls were made per-rule with no consistent reasoning. Added an explicit, uniform policy to the file's header comment (precision, severity, type-naming criteria) and swept every rule into compliance:
    • Precision: facebook-access-token and mapbox-secret-token are now keyword-gated (their bare patterns had empirically-confirmed false-positive risk). openai-api-key's optional proj-/svcacct- group is now unconditionally required; the bare legacy sk- form moved to a new keyword-gated openai-api-key-legacy rule so older-format keys are still caught, just with the same evidence bar as everything else.
    • Severity: docker-hub-pat high → critical (registry publish access is the same supply-chain risk class as npm-token/pypi-token). linear-api-key/airtable-pat/notion-integration-token critical → high (SaaS workspace data access, not infra/code/money control). connection-string-credential high → critical (a live DB credential is direct production data access).
    • Naming: discord-webhook-url's and slack-webhook-url's type now match their id exactly (discord_webhook → discord_webhook_url, slack_webhook → slack_webhook_url), changing their sanitized placeholder names accordingly.
    • .plan/ (internal PRD/spec/plan/roadmap docs) is no longer tracked in git, kept locally, .gitignored going forward.
    • scanner.py's six internal-only helpers (compute_fingerprint, safe_preview, disabled_rule_ids, apply_allow_paths, apply_severity_overrides, apply_config_filters) are now underscore-prefixed. The module previously exposed 14 public-looking functions when only scan is public API.
    • The package version now has a single source of truth: pyproject.toml reads it dynamically from oneleaks/__init__.py, so oneleaks --version and the packaged metadata cannot drift.
    • Makefile consolidated from 17 targets to 13: lint now absorbs the old format-check+typecheck, test always runs with coverage (absorbing test-cov), install also installs the pre-commit hook (absorbing precommit-install), and the rarely-used all target was removed. .github/workflows/ci.yml now calls make lint/make test/make docs-build instead of duplicating the underlying commands.
    • Docs nav grouped into Getting Started / Guides / Advanced / Reference sections instead of one flat list.

    0.1.0 - 2026-08-08¶

    Added¶

    • Initial implementation of the v0.1 scope: oneleaks.scan() / oneleaks.sanitize() / oneleaks.desanitize() Python API and oneleaks CLI.
    • Detection engine: rule registry (built-in, YAML, JSON, and Python rules), regex matching with keyword-context gating, generic credential-assignment detection, Shannon-entropy detection, structural-anchor detection (PEM private keys, JWTs, connection-string credentials), and priority-based overlap resolution.
    • ~20 built-in provider secret rules (AWS, GitHub, GitLab, OpenAI, Anthropic, Slack, Stripe, Twilio, Datadog, Google, Azure, PyPI, npm) and 7 PII detectors (email, phone, SSN, credit card, IPv4, IPv6, IBAN) with real validators (Luhn, IBAN Mod-97, SSN, ipaddress, JWT structure).
    • Safe findings: type-specific masked previews, HMAC-SHA256 fingerprints.
    • Sanitization: typed numbered placeholders, referential consistency, optional reversible mapping export (reveal=True, seed_mapping) and desanitize().
    • File and directory scanning with binary/size/exclude filtering, plus .oneleaks.yaml config with strict unknown-field rejection.
    • Inline suppression (# oneleaks: allow), path/rule exclusions and allowlisting.
    • Git integration: scan_changed() / scan_staged().
    • CLI: scan / sanitize / desanitize subcommands, stdin/stdout, --json, --fail-on, --map, exit codes.

    Known gaps¶

    • pii_ml=True is declared as an installable extra but not yet wired to a Presidio adapter.
    • severity_overrides in config is parsed but not yet applied to findings.
    • Rule-level include_paths / exclude_paths are parsed but not yet enforced.
    • Full positive/negative/boundary test coverage across all built-in provider rules, Hypothesis property tests, and performance benchmarks are still outstanding.
