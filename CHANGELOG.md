# Changelog

All notable changes to this project are documented in this file. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versioning follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added
- **20 new built-in provider/structural secret rules**: AI/dev-tool (`huggingface-token`, `replicate-api-token`, `groq-api-key`), cloud/infra (`aws-temp-access-key-id`, `digitalocean-pat`, `cloudflare-api-token`, `vault-service-token`, `docker-hub-pat`), SaaS (`sendgrid-api-key`, `postman-api-key`, `sentry-auth-token`, `newrelic-api-key`, `planetscale-token`, `supabase-access-token`, `shopify-access-token`), messaging (`discord-bot-token`, `discord-webhook-url`, `telegram-bot-token`), and structural anchors (`pgp-private-key`, `http-basic-auth-credential`). **3 new PII rules**: `imei` (validated via the existing `luhn` validator, which is also IMEI's real check-digit algorithm), `mac-address`, and `bank-routing-number` (keyword-gated, new `aba_routing` validator). All three new PII types are toggleable via `.oneleak.yaml`'s `pii:` block like the existing seven.
- **13 more built-in provider secret rules** (second batch): `terraform-cloud-token`, `google-oauth-client-secret`, `heroku-api-key` (keyword-gated), `mailchimp-api-key`, `square-access-token`, `square-oauth-secret`, `stripe-webhook-secret`, `linear-api-key`, `notion-integration-token`, `airtable-pat`, `mapbox-secret-token`, `algolia-admin-api-key` (keyword-gated), `facebook-access-token`. `mapbox-secret-token` and `facebook-access-token` are lower-confidence than the rest of the rule set (approximate format / short 3-char prefix respectively) and are candidates for revisiting if they prove noisy in practice.
- Project tooling: `Makefile`, GitHub Actions CI, tag-triggered PyPI trusted-publish workflow, pre-commit dogfooding config, MkDocs + Material docs site.
- `severity_overrides` in `.oneleak.yaml` is now applied to findings (previously parsed but unused). Values are validated against the known severity levels.
- **Git history scanning**: `oneleak.git.scan_history()` / `oneleak scan --history` scans commit history for secrets, including ones later removed from the working tree, something `scan()`/`scan_changed()`/`scan_staged()` cannot see, since they only look at current content. Defaults to the current branch's history capped at the most recent 5000 commits (`--since`/`--max-commits`/`--all-refs` to override). Truncation is always reported, never silent. Detection runs per-commit, per-diff-hunk (only what each commit actually added, with each hunk's added lines joined into one block so multi-line formats like PEM keys still match correctly), not a full-file rescan at every commit. `Finding.commit` and `ScanResult.truncated` are new fields supporting this.
- **MCP server** (`oneleak[mcp]`, `oneleak-mcp` command): exposes `scan_text`, `scan_path`, `sanitize_text`, `desanitize_text` as MCP tools over stdio, for agent runtimes to call directly instead of shelling out to the CLI. Config auto-discovery matches CLI behavior. See `docs/mcp.md`.
- Provider rule test coverage for GitLab, Slack, Twilio, Datadog, Google, and PyPI (positive/negative/boundary cases).
- Hypothesis property tests (`tests/test_properties.py`): Luhn, IBAN, sanitization offsets, overlap resolution, and config-schema validation.
- `scripts/benchmark.py` / `make bench`: prints timing for 1KB/1MB text, a config-sized input, small/large synthetic repos, and `git.scan_changed()`. An observability script, not a CI gate.
- `AGENTS.md`: repo orientation for coding agents (setup, commands, load-bearing ordering decisions, conventions).
- `docs/architecture.md`: detailed explanation of the detection pipeline and sanitization algorithm, stage by stage. The "advanced" doc previously only in internal (untracked) notes.
- `.github/workflows/docs.yml` + `make docs-deploy`: publishes docs to GitHub Pages on push to main. Read the Docs (the primary host) still builds via its own webhook once connected, and no GitHub Action can drive that directly, but this workflow optionally triggers an RTD API build too, if `RTD_API_TOKEN`/`RTD_PROJECT_SLUG` are configured.
- Explicit `[tool.ruff.lint] select` in `pyproject.toml` (including `I`, isort-equivalent import sorting) instead of relying on the installed ruff version's implicit default rule set.

### Fixed
- **`.oneleak.yaml` fields weren't shape-checked before use.** `exclude`, `rule_paths`, `disabled_rules`, `allow.paths`, `pii`, and `severity_overrides` all skipped validating that the YAML gave the expected shape. A list field given as a bare string (`exclude: "node_modules/**"` instead of `["node_modules/**"]`) silently iterated it character-by-character instead of raising, making the field a silent no-op. A mapping field given as a list (`pii: [email, phone]` instead of `{email: true, phone: true}`) crashed with a raw `ValueError`/`AttributeError` instead of a clean error. Both cases now raise `ConfigError` naming the offending field. Both failure modes fail toward *more* scanning, not less: a broken `exclude`/`allow.paths` scans more than intended rather than silently missing secrets.
- Baseline files written by `write_baseline()` stamp a `version` field that `load_baseline()` never checked. A baseline from an incompatible future format would have been read as if it matched the current one. `load_baseline()` now rejects a mismatched or missing version with a clear error.
- A PGP private key block (`pgp-private-key`) got a useless generic preview (`----****---`) instead of the clean `<PRIVATE_KEY>` a PEM key gets, since `_safe_preview()`'s private-key branch only matched `pem-private-key`'s `type`, not `pgp-private-key`'s.
- **The same unchecked-shape problem existed in custom YAML/JSON rule loading, worse: several cases weren't even caught by `ConfigError`.** `priority: "high"` (a string instead of an int) parsed cleanly and then crashed deep inside overlap resolution with a raw, unhandled `TypeError`. `pattern: [...]`/`validator: [...]` (a list instead of a string) crashed the same way in candidate generation. `id`/`category`/`type`/`severity` given as a non-string (e.g. `id: 123`) went undetected entirely. Worst of the group: `keywords: "xyz"` (a bare string instead of a list, a very plausible typo) didn't error at all — it silently split into individual-character keywords (`tuple("xyz") == ('x','y','z')`), which then matched almost any nearby text containing a common letter, quietly defeating the keyword gate a rule relies on for precision instead of raising. `rules.py::_validate_entry()` now shape-checks every field before `build_rule()` trusts it.
- Several provider secret regexes (`openai-api-key`, `anthropic-api-key`, `stripe-secret-key`, `stripe-restricted-key`, `pypi-token`, plus the entropy-candidate regex) used unbounded quantifiers that could run away across trailing content with no separator. Bounded them to a realistic max length.
- Inline `# oneleak: allow <rule-id>` suppression ran *after* overlap resolution, so scoping suppression to one rule could accidentally suppress a different, non-allow-listed rule's finding for the same span. Suppression now runs before overlap resolution.
- `azure-storage-key`'s regex had an unsatisfiable trailing word-boundary and could never match anything.
- `aws-secret-access-key`'s bare 40-character charset match could shift across the `=` delimiter in `KEY=value`, capturing the wrong span. Now anchored on the key name + assignment operator.
- A YAML/JSON custom rule with `keywords:` (or other list fields) present but null crashed with an unhandled `TypeError` instead of a clean `ConfigError`.
- `oneleak.scan(bytes)` on non-UTF8 input raised unconditionally, unlike an equivalent binary file on disk (silently skipped). The two input forms now behave consistently.
- `sanitize()` (like `git.scan_changed()`/`scan_staged()` before it) called the scanner directly and bypassed `.oneleak.yaml`'s `disabled_rules`/`allow.paths`/`severity_overrides`. All three entry points now share one code path (`scan_text_with_config()`), closing this class of bug for good rather than patching each call site.
- CLI: `oneleak scan <path> --changed`/`--staged` now errors instead of silently ignoring the path argument, and `--changed`/`--staged` together is now a clean argparse error instead of `--changed` silently winning.
- The generic-assignment detector's bare `token` keyword false-positived on non-secret values like GitHub Actions' `permissions: { id-token: write }`. `read`/`write` added to the placeholder-value denylist.

### Removed
- Dropped several unused/never-wired fields found during a bug + simplification pass: `Rule.min_entropy`, `Rule.python_rule`, `Finding.confidence`, `RuleMatch.confidence`, `Config.sanitize`, `Rule.include_paths`/`exclude_paths`. All were parsed/declared but never consumed anywhere in the detection pipeline. `PythonRule.detect()` now only accepts `RuleMatch`, not a bare `(start, end)` tuple, removing a branch used by nothing in practice.
- Dropped the `oneleak[pii-ml]` optional-dependency group until there's an actual adapter behind it. It was pure packaging plumbing with no code path.

### Added
- `oneleak --version`, and a real `description` on `oneleak --help` (which previously said nothing about what the tool does).
- `Config` and `RuleMatch` are now exported from the top-level `oneleak` namespace. Previously the documented custom-rule example needed two import paths (`from oneleak import PythonRule` + `from oneleak.models import RuleMatch`). You could not implement the exported `PythonRule` without a non-exported type.
- **Baselines**: `oneleak scan --baseline PATH [--update-baseline]` records `(rule_id, path, fingerprint)` for known findings and only reports new ones, the standard adoption path for turning oneleak on against a codebase that already has findings. New module `oneleak/baseline.py`. Requires `ONELEAK_FINGERPRINT_KEY` to be set (fingerprints are otherwise keyed off a random per-process value, so a baseline could never match across runs). `--baseline` refuses to run without it rather than silently matching nothing. Deliberately a CLI-only concept, not a `Config`/`.oneleak.yaml` field: a baselined finding is still a real secret, and routing it through the shared config-filter pipeline would have silently stopped `sanitize()` from redacting it too. See `docs/configuration.md#baselines`.
- `docs/concepts.md`: the field knowledge behind oneleak's design decisions (entropy, validators, fingerprinting, redaction vs. tokenization, baselines, and why some competitor techniques, like TruffleHog-style live verification and Betterleaks-style BPE token-efficiency scoring, were evaluated and not adopted).
- `docs/configuration.md` documents how to adopt oneleak on a repo that already has findings, now via baselines rather than only partial substitutes.

### Fixed
- **Every "bad input file" path leaked a raw Python exception type to the user.** `--config missing.yaml` printed `error: FileNotFoundError: [Errno 2]...`, a malformed `.oneleak.yaml` printed a multi-line `ParserError` dump, a malformed `--map` file printed `JSONDecodeError`, and a mapping file missing a key printed `KeyError: 'rule_id'`. All now raise `ConfigError` with a message that names the offending file and the actual problem. Fixed at the source (`config.py`, `rules.py`, `cli.py`) rather than in the CLI's catch-all, so the Python API benefits too: `oneleak.scan(text, config="missing.yaml")` previously raised `FileNotFoundError`.
- `oneleak scan --staged` outside a git repository dumped git's entire multi-thousand-character usage text (outside a repo, `git diff --cached` falls back to `--no-index` mode where `--cached` is not a valid option). All three git modes now fail fast and identically with `error: not a git repository`, and any other git failure is truncated rather than echoed in full.
- Git errors no longer echo back the internal command oneleak happened to run (`git log --format=%H,%P failed: ...` is an implementation detail, not something a user can act on).

### Changed
- **Secrets and PII split into peer modules, `oneleak/secret_rules.py` and `oneleak/pii_rules.py`.** Each owns its own builtin rule file's loading; everything else (matching engine, validators, overlap resolution, fingerprinting, sanitization) stays shared, category-agnostic code, since e.g. `_resolve_overlaps()` genuinely needs both categories' candidates in one pool (a connection-string password can look like an email's `local@domain` shape). This also fixes a real bug: the `pii:` config toggle used to validate against a hand-maintained set in `config.py` while `scanner.py` separately hand-maintained the type→rule_id map it disabled by, and if the two ever drifted, a type would pass validation and then silently do nothing. Both are now derived from `pii_rules.py`'s one source of truth (`pii.yaml` itself), so a new builtin PII rule is automatically toggleable with no matching Python edit required, and this class of drift is no longer possible. No new config surface: secrets deliberately did not get an equivalent `secrets: {}` toggle, since `disabled_rules: [rule-id]` already covers that uniformly for every rule regardless of category. `pii.yaml` also gained the policy header comment `secrets.yaml` already had, describing the two things that are genuinely different about PII rules (evidence favors checksums over fixed prefixes; severity trends low/medium, not high/critical).
- **`secrets.yaml` consistency pass.** The file previously had no written standard for when a rule needs a keyword gate or what severity a given access level should get, so those calls were made per-rule with no consistent reasoning. Added an explicit, uniform policy to the file's header comment (precision, severity, `type`-naming criteria) and swept every rule into compliance:
  - Precision: `facebook-access-token` and `mapbox-secret-token` are now keyword-gated (their bare patterns had empirically-confirmed false-positive risk). `openai-api-key`'s optional `proj-`/`svcacct-` group is now unconditionally required; the bare legacy `sk-` form moved to a new keyword-gated `openai-api-key-legacy` rule so older-format keys are still caught, just with the same evidence bar as everything else.
  - Severity: `docker-hub-pat` high → critical (registry publish access is the same supply-chain risk class as `npm-token`/`pypi-token`). `linear-api-key`/`airtable-pat`/`notion-integration-token` critical → high (SaaS workspace data access, not infra/code/money control). `connection-string-credential` high → critical (a live DB credential is direct production data access).
  - Naming: `discord-webhook-url`'s and `slack-webhook-url`'s `type` now match their `id` exactly (`discord_webhook` → `discord_webhook_url`, `slack_webhook` → `slack_webhook_url`), changing their sanitized placeholder names accordingly.
- `.plan/` (internal PRD/spec/plan/roadmap docs) is no longer tracked in git, kept locally, `.gitignore`d going forward.
- `scanner.py`'s six internal-only helpers (`compute_fingerprint`, `safe_preview`, `disabled_rule_ids`, `apply_allow_paths`, `apply_severity_overrides`, `apply_config_filters`) are now underscore-prefixed. The module previously exposed 14 public-looking functions when only `scan` is public API.
- The package version now has a single source of truth: `pyproject.toml` reads it dynamically from `oneleak/__init__.py`, so `oneleak --version` and the packaged metadata cannot drift.
- `Makefile` consolidated from 17 targets to 13: `lint` now absorbs the old `format-check`+`typecheck`, `test` always runs with coverage (absorbing `test-cov`), `install` also installs the pre-commit hook (absorbing `precommit-install`), and the rarely-used `all` target was removed. `.github/workflows/ci.yml` now calls `make lint`/`make test`/`make docs-build` instead of duplicating the underlying commands.
- Docs nav grouped into Getting Started / Guides / Advanced / Reference sections instead of one flat list.

## [0.1.0] - 2026-08-08

### Added
- Initial implementation of the v0.1 scope: `oneleak.scan()` / `oneleak.sanitize()` / `oneleak.desanitize()` Python API and `oneleak` CLI.
- Detection engine: rule registry (built-in, YAML, JSON, and Python rules), regex matching with keyword-context gating, generic credential-assignment detection, Shannon-entropy detection, structural-anchor detection (PEM private keys, JWTs, connection-string credentials), and priority-based overlap resolution.
- ~20 built-in provider secret rules (AWS, GitHub, GitLab, OpenAI, Anthropic, Slack, Stripe, Twilio, Datadog, Google, Azure, PyPI, npm) and 7 PII detectors (email, phone, SSN, credit card, IPv4, IPv6, IBAN) with real validators (Luhn, IBAN Mod-97, SSN, `ipaddress`, JWT structure).
- Safe findings: type-specific masked previews, HMAC-SHA256 fingerprints.
- Sanitization: typed numbered placeholders, referential consistency, optional reversible mapping export (`reveal=True`, `seed_mapping`) and `desanitize()`.
- File and directory scanning with binary/size/exclude filtering, plus `.oneleak.yaml` config with strict unknown-field rejection.
- Inline suppression (`# oneleak: allow`), path/rule exclusions and allowlisting.
- Git integration: `scan_changed()` / `scan_staged()`.
- CLI: `scan` / `sanitize` / `desanitize` subcommands, stdin/stdout, `--json`, `--fail-on`, `--map`, exit codes.

### Known gaps
- `pii_ml=True` is declared as an installable extra but not yet wired to a Presidio adapter.
- `severity_overrides` in config is parsed but not yet applied to findings.
- Rule-level `include_paths` / `exclude_paths` are parsed but not yet enforced.
- Full positive/negative/boundary test coverage across all built-in provider rules, Hypothesis property tests, and performance benchmarks are still outstanding.
